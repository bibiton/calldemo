# 00 — 決策原則：成本優先、UX 底線

## 1. 排序

1. **UX 底線**（否決權）：任何選項只要讓顧客、店員或面板的體驗變差，直接淘汰，不進入成本比較。
2. **成本最低**：通過 UX 底線的選項中，選每月成本（含規模放大後）最低者。
3. **同成本時**：選維運較簡單、可逆性較高者。

「UX 變差」不是感覺，是下列可觀察的事件：

| 對象 | UX 底線（任一違反即否決） |
|---|---|
| 顧客 | 叫到號卻沒收到任何提醒（頁面開著或已訂閱推播時）；取號需要下載 App 或註冊帳號；取號步驟 > 3 步；畫面在手機直立時無法完整操作 |
| 店員 | 按「叫下一號」到面板出現 > 1 秒（正常網路）；斷線後狀態錯亂需重新整理；登入步驟拖慢交班 |
| 面板 | 叫號沒有聲音或聲音每台不一致；斷網時黑畫面；QR 被廣告蓋住或在 2～3 公尺外掃不到 |
| 門店管理 | 停用／到期生效不明確；看不到即時隊列 |

## 2. 成本的根本事實（推導起點）

以下皆為 2026-10-27 查證之 Cloudflare 計費規則（來源見 02-cost-model）：

- DO **duration 以 wall-clock 計費、且一律以 128 MB 計**；可 hibernate 而閒置的 DO **不計 duration**。
  → 結論：DO 是否能睡著，決定了成本是「幾乎 0」還是「每店每月 $4」。
- DO 收到的 WebSocket 訊息以 **20:1** 折算成 request。
  → 結論：高頻的人員操作走 WebSocket 進 DO，比每次打 HTTP 便宜 20 倍，而且延遲更低。
- `setWebSocketAutoResponse` 回應時**不喚醒 DO、不計 duration**。
  → 結論：心跳必須用它，不能讓 DO 自己回 pong。
- 靜態資產請求（Pages / Workers static assets）**免費且無上限**。
  → 結論：前端放 Pages，不用 SSR。
- R2 **出口免費**；KV 寫入 $5／百萬，是讀取的 10 倍；KV 同一 key 每秒最多 1 次寫入。
  → 結論：KV 只放「很少改、很常讀」的東西（開通狀態），即時狀態絕不放 KV。

## 3. 決策檢查表（每個設計／PR 都要過）

- [ ] DO 內沒有 `setTimeout` / `setInterval`；定時工作只用 `storage.setAlarm()`，且一天最多數次
- [ ] WebSocket 用 `ctx.acceptWebSocket()`，沒有 `ws.accept()`
- [ ] 心跳走 `setWebSocketAutoResponse`，客戶端送的是**文字訊息** `ping`（瀏覽器無法送協定層 ping frame）
- [ ] 面板與人員端不輪詢 API
- [ ] DO 內沒有對外 `fetch`（外部呼叫走 Queues）
- [ ] 即時寫入都在 DO SQLite，D1 只收「結束後」的批次
- [ ] 沒有每個請求寫 KV
- [ ] 新增的 Cron／Alarm 頻率已算過成本
- [ ] 新畫面在 360×640 直立手機可完整操作
- [ ] 個資只存必要欄位、有明確刪除時點
- [ ] 此變更若在 500 店規模下，成本增量已估算並寫進 02-cost-model

## 4. 每個決策要寫的內容

DECISIONS.md 每條 ADR 都必須有：背景、選項、每月成本估算（至少 50 店，必要時 500 店）、UX 影響、決定、理由。
